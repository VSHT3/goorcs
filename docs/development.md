# Development workflow

## Setup

1. Install the standard Godot **4.7.2 stable** executable from the [official downloads](https://godotengine.org/download/). Keep collaborators on the same version; upgrade deliberately.
2. Clone the private repository and import `project.godot` into Godot.
3. Run the main scene with F5. Choose **Sandbox** to test freely, or **Play** for normal rules.

No Node.js, .NET SDK, external packages, export templates, or MCP servers are required to run the current project in Godot. Export templates will be needed when distributing desktop builds.

The commands below assume the Godot binary is available as `godot`; substitute its absolute path if necessary.

```sh
./tools/run.sh           # Refresh imports/classes, then run the actual game.
godot --editor --path .  # Open the editor; F5 also runs after its import scan.
```

Use `./tools/run.sh` for terminal launches after pulling friends' changes. It runs a headless editor import before starting the game, refreshing the ignored local `.godot` class registry and imported assets. `GODOT_BIN=/path/to/godot ./tools/run.sh` selects another executable; extra arguments are passed to the game. Run as your normal desktop user, not through `sudo`.

Direct `godot --path .` does not perform the editor's project scan. A stale cache can therefore omit newly pulled `class_name` scripts, producing cascading “Could not find type” / “Could not resolve external class member” parse errors. If the main script cannot load, its menu button signals are never connected. Refresh with `godot --headless --editor --import --path .` before a direct launch, or open the editor and let its scan finish. Do not commit `.godot` or delete player saves to repair this.

### Single-command verification

Install **Python 3.10 or newer** for development verification; its standard library is sufficient. Python is not a game/runtime dependency. The runner supports macOS and Linux and requires the exact official standard-engine build `4.7.2.stable.official.ed1daf0bf`; `godot --version` reports that string. A different release or custom build fails the version gate rather than silently changing test behavior.

From the repository root:

```sh
python3 tools/verify.py headless  # Import, save-isolation/startup gates, and every headless test.
python3 tools/verify.py rendered  # Import, save-isolation/startup gates, and every rendered test.
python3 tools/verify.py all       # Both modes in one isolated project.

# Override the executable with either --godot or GODOT_BIN.
python3 tools/verify.py all --godot /Applications/Godot.app/Contents/MacOS/Godot
GODOT_BIN=/path/to/godot python3 tools/verify.py headless
```

Each invocation copies the project into a disposable temporary directory without `.godot`, so it exercises fresh resource imports and never changes the working project's editor/import cache. Only that copy receives a unique application/save-directory identity, including the Windows/macOS setting variants; inherited `HOME`, XDG directories, and temporary directories point into the disposable workspace. Before startup or tests, an engine probe must report an actual `user://` directory inside that workspace. Separate host/client workers inherit the copied project and environment. Your normal collection, audio and Discord preference saves are neither copied nor overwritten. The disposable copy also sets `discord/application_id=0`, preventing tests from publishing activity to your desktop Discord client. Do not replace this isolation with an unverified `--user-data-dir` flag, and do not run individual scripts directly against your personal project when preserving saves matters.

Discovery recursively includes every `tests/**/*_test.gd`. Tests default to **headless**; the explicit `RENDERED_TESTS` set in `tools/verify.py` classifies the pixel/renderer-dependent board, tower-icon, horde, enemy-inspection, and menu-wordmark suites. Add future rendered suites to that set. Scripts named `*_worker.gd` run only through their owning real-peer tests, never standalone. Any other `.gd` under `tests/` is an error until classified/renamed; removed rendered entries also fail discovery. The console and `inventory.json` list every selected test, other-mode test, and worker, so a mode never silently claims the other mode's coverage.

Checks run sequentially. Every invocation first gates the engine version, import (300-second limit), and actual save isolation (30 seconds); each requested mode gates main-scene startup (30 seconds) before its tests. Tests have a 180-second limit each; use `--timeout SECONDS` and `--import-timeout SECONDS` for slower machines. A failed gate stops dependent checks; failed tests do not prevent later tests in that mode from running. Nonzero exits, timeouts, Godot error diagnostics even with exit zero, and missing `PASS:` markers fail verification. Intentionally error-emitting negative tests must declare exact expected diagnostic bodies and counts in `EXPECTED_ERRORS`, keyed by test path; unexpected or missing diagnostics still fail. Do not exempt an entire suite or all `push_error` output.

`project.godot` clears `gui/theme/custom_font` only for Godot's `editor_hint` feature. Clean editor/import startup therefore does not request font data before importing it; running the game still uses the bundled Pixelify font. Both `tools/run.sh` and verification import the actual project settings without temporary font-setting rewrites or diagnostic exemptions.

Logs are retained under ignored `.verify-logs/<UTC timestamp>-<mode>-<unique suffix>/`, including per-check commands, combined stdout/stderr, engine logs, test inventory, `summary.json`, and surviving worker logs after a failure/timeout. Choose a new custom location with `--log-dir PATH` (the directory must not already exist). Temporary project/import/save data is removed on completion or interruption; durable logs remain for inspection. Timeout, Ctrl-C, and SIGTERM cleanup terminates all discovered spawned process groups, including detached Godot host/client sessions. The runner tracks descendants and its unique workspace marker because Godot's Unix `OS.create_process()` starts a new session. Uncatchable termination (SIGKILL, a power loss, or forced OS shutdown) cannot run cleanup.

Process discovery restricts ownership to the current user, excludes zombie/dead processes, and ignores nonpositive/special process-group IDs. Before each cleanup phase, tracked groups are intersected with a fresh snapshot of live owned groups; a permission error triggers another snapshot so an already-exited group is not mistaken for failed cleanup. If signaling a still-live group fails, cleanup continues through every other group and the final kill phase, then reports the group ID and signal failure.

**Rendered mode needs a real graphical display and Compatibility/OpenGL renderer.** On a macOS desktop it opens test windows; a locked/headless login or missing OpenGL support may fail. Headless success proves neither pixel output nor native desktop interactions. On Linux, install Xvfb, Xauth, and Mesa software OpenGL to run without a physical display:

```sh
LIBGL_ALWAYS_SOFTWARE=1 GALLIUM_DRIVER=llvmpipe \
  xvfb-run --auto-servernum --server-args="-screen 0 1280x720x24" \
  python3 tools/verify.py all
```

Prefer the Xvfb command for automated Linux `rendered`/`all` runs even when a desktop is available: its test windows stay on a separate virtual display instead of opening over the player's work. This preserves rendering coverage; changing those suites to Godot `--headless` would remove the pixels they verify. Reserve desktop windows for intentional manual playtests.

Verification runs locally using the commands above; the GitHub Actions verification workflow has been removed. Software-rendered pixels are regressions, not proof of native GPU/driver behavior, desktop input/focus feel, sound output, performance, or internet reachability. Continue real-game inspection and separate-machine/network playtests where those claims matter. Native Windows runner/process-tree cleanup is not implemented; use Linux/WSL for automation and separately playtest the native game.

Host with a numeric IP address your friend can reach:

- Same LAN: use the host's LAN address and allow the selected UDP port through its firewall.
- Private VPN/network: both players must already belong to that network; advertise the host's VPN address. Tailscale is an optional example, not installed or configured by this game.
- Public internet: advertise the public/routable address. Forward the chosen UDP port to the host computer if required and allow it through the firewall. Carrier-grade NAT may prevent forwarding; this game does not solve it.
- Two processes on this computer: use `127.0.0.1`. That address cannot connect a friend on another machine.

The Host IP field shows the most likely LAN address: physical Wi-Fi/Ethernet private addresses first, then other physical, other private (often VPN tunnels), other addresses, and virtual machine/container adapters last (`vEthernet`/WSL/Hyper-V, Docker, VirtualBox, VMware, libvirt, LXC). Old single-address `GORCS1` codes remain valid. ### Enemy sends and income

`MatchCombat.send_enemy(slot, type_id)` owns its atomic purchase/delivery/income rule. `MatchPlanning` first validates admitted sender, allowed payer, and planning commitment, then calls that owner; host-player and guest commands share this path. Unknown IDs or rejected/readied sends spend nothing and create no orders. Clients cannot grant currency, enemies, or authoritative speed.

`CombatRules.catalog.enemies` registers `EnemyDefinition` resources through `resources/content_catalog.tres`, owning identity, description, damage, health/speed multipliers, regular-wave composition constraints, send price/income, and artwork. `prototype.tres` owns regular-wave values and the baseline `send_spawn_interval` (0.35 simulation seconds). `MatchCombat` captures that positive finite baseline and interval-progression settings on admission; invalid cadence rejects purchase/start without mutation. Each target board has one FIFO with its own next-delivery time. Planning reserves orders without route access; starting combat delivers only its first order at time zero. Live purchases append to the same FIFO, delivering immediately only when that destination's cooldown permits. An idle stream restarts at the current host time, never backdated or burst-releasing idle slots.

Regular and sent streams consume separate clocks. Due events merge chronologically per board so coarse ticks retain actual portal order and shortest-branch rotation; regular events win equal-time ties during advancement. Each newly delivered enemy gets fractional travel from its scheduled time and its own speed. Sends never consume regular roster budget, unlock/count/share limits, timetable slots, spawn counters, or RNG draws. Both streams use ordinary enemy routes, targeting, bounties, and leak damage. Both pending send FIFOs and living enemies must empty before a surviving both-board clear pays the regular reward plus each sender's recurring income once. Ordinary sends grow income at purchase; paid bosses permanently reduce it and require enough existing income to cover the entire penalty. Neither grants immediate income Coins, and terminal defeat pays no clear reward. Reset removes queues, cooldowns, income, and enemies.

The header has one **Send** button, host-owned Coin price/signed income change, and the existing local type selector. Footer `Income +N`, `In N`, and `Out N` appear only when nonzero; counts mean pending deliveries in either phase, not a next-wave-only queue. Camera keys yield to selector/targeting popups; regular spawn progress excludes sends.

Combat sends now always belong to that combat. [Repository](https://github.com/Coding-Solo/godot-mcp)

MIT-licensed bridge for launching Godot, capturing debug output, and basic scene/resource operations. During tool evaluation, its current source successfully reported the engine version, created a scene, and added a node; Godot then ran that generated scene headlessly. Its inspected tool list did not include screenshot capture or input simulation.

It is not installed in this project.

### Godot MCP Pro

[Asset listing](https://godotengine.org/asset-library/asset/4961) · [Repository](https://github.com/youichi-uda/godot-mcp-pro)

Candidate for screenshots, input simulation, and live game inspection. The public repository provides the editor addon; the required server is distributed in a paid package. Advertised runtime capabilities have not been independently verified for this project. Use matched addon/server versions if adopted.

Before relying on it, verify actual game screenshots, UI input and state changes, runtime error retrieval, and how separate multiplayer instances are targeted. A bridge does not remove the need for a working graphical runtime.

Keep development automation local, enable available connection authentication, and never expose editor-control ports as part of the game's multiplayer service. Ensure development-only tooling is excluded from distributed builds.

## Pixel-art asset workflow

**PixelLab sprites are development-time assets.** The game ships a cleaned user-supplied chest pair and accepted tower PNGs. Arrow tower was generated through the PixelLab API using locally supplied credentials; there is no persistent API/MCP integration or runtime network dependency. `API.txt` is ignored and must never be committed or distributed. Retro Diffusion remains an untested comparison option. Use Aseprite or Pixelorama for further manual cleanup.

For the verified local ComfyUI/Klein setup, agent/API generation steps, iterative reference editing, and sprite exports, see the [AI-to-sprite pipeline](sprite-pipeline.md). Local Rune level-two candidates are not accepted runtime replacements; the current game art remains the accepted PNGs described below.

- [PixelLab](https://www.pixellab.ai/) documents MCP/API access, directional characters, animation, transparent objects, editor integrations, and Godot tileset guides. Its free trial lists API/MCP access but excludes map tools.
- [Retro Diffusion](https://retrodiffusion.ai/) also documents a hosted MCP server, API access, reference-based generation, animations, and tilesets. Automation is not exclusive to PixelLab.
- At the time of assessment, PixelLab listed paid tiers at $12/$24/$50 per month. Retro Diffusion listed images at $0.03/$0.06/$0.18 depending on model, with animations from $0.07 and free starting balance. Recheck current pricing and terms before spending. PixelLab generations are billing units, not necessarily finished images; directional sets and animations may consume several.

## Collection and chest verification

Collection unlocks are stored in `user://collection.json`, separate from unsaved workshop layouts. Gorcs retains the existing collection directory through Godot's custom user-directory settings so the name correction does not reset progress. On Linux this remains `~/.local/share/godot/app_userdata/Goorcs/collection.json`; Windows/macOS overrides retain their previous `Godot/app_userdata/Goorcs` directories. The legacy directory spelling is internal storage, not displayed branding. Godot's resolved user-data path is authoritative; preservation was verified on Linux. Use one game instance at a time for this save. There is no cloud sync or concurrent-writer coordination.

Opening chooses rewards in `CollectionStore`, writes a sibling temporary file, and renames it over the previous save before committing the in-memory grant. The reveal receives that saved result and cannot change it. Unknown versions/IDs, malformed data, unreadable files, or write failures block openings with a visible error. Long error details are selectable and scrollable. Repair or move aside a damaged save and restart; the game never silently resets it. Moving the file aside starts a new collection, so preserve a copy if its unlocks matter.

**Reset progress** in the collection screen opens a confirmation dialog. Confirming persists an empty unlocked set through the same atomic save operation before clearing memory and the previous reveal; Cancel changes nothing. The workshop layout is unaffected. Reset is disabled during a reveal, when there are no unlocks, or while the save has an error. A failed reset preserves both the existing save and in-memory unlocks.
