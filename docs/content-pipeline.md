# Tower and enemy content pipeline

## One registration owner

`resources/content_catalog.tres` is the explicit, typed `ContentCatalog` registration resource. Its `towers` and `enemies` arrays are the only shipped content lists. Array order is presentation order. `CombatRules.catalog` references it; custom rules may reference another catalog.

A tower entry is a `TowerDefinition` that references its `TowerReward` identity/art resource. Collection rewards are derived from those entries, not registered separately. The match palette and both `PathBoard` renderers use the rules' catalog. Enemy send choices and inspection stats come from the accepted host snapshot; artwork comes from the same local catalog. Both peers must ship matching IDs and art. Resources are local project assets, not downloaded or sent by the host.

Host commands validate admitted loadouts, ownership, funds, phase, and stable IDs. `MatchCombat` captures scalar stats and deep-copies nested behavior/evolution/upgrade/roll configuration on admission, then publishes detached snapshots; editing a source resource or a received snapshot cannot retune an admitted match. Collection saves retain their existing version and stable tower IDs. Arrow is the guaranteed starter: atomic migration preserves existing unlocks, and collection reset restores the starter. Never rename or remove a saved ID without an explicit save migration. Guest collection ownership is a local-save claim in this trusted-friends game, not remote account/save attestation; the host validates and freezes the admitted deck and enforces it on every purchase.

## Add a tower using an existing role

1. Create `resources/collection/<id>.tres` with the `TowerReward` script. Give it a unique, nonempty stable `id`, title, description, icon/atlas texture, and accent. Collection/chest icons automatically frame the texture's opaque bounds; retain the original board texture coordinates when authoring anchors, rigs, and projectile origins.
2. Set the reward's `board_height` (opaque height in cells) and normalized `board_anchor` (foot/base anchor). These drive drawing, shadows, and camera headroom without changing the one-cell gameplay footprint.
3. For direct projectiles, set `projectile_length` in cells and `projectile_width` in pixels. `projectile_origin` is a texture-local fallback muzzle; negative uses the ordinary centered origin. Animated archers supply optional board-only `board_texture`, `archer_head_texture`, `archer_body_texture`, and `archer_pivot`, plus `secondary_sprite_offset`/`additional_archer_offsets` in the icon's texture-local space. The head sheet has eight 16×14 directional frames; the body has four 14×14 frames. Collection `icon_texture` stays unchanged. The shared rig computes held tips and captures normalized release origins; no tower-ID switch or obsolete baked-region alias remains.
4. Create `resources/combat/towers/<id>.tres` with the `TowerDefinition` script and reference the reward. Configure price, base upgrade price, positive range/interval, damage upgrade bonus, and a speed-upgrade multiplier between zero and one. Attack/chain damage must be positive; passive damage may be zero (as in the shipped support/economy definitions) but never negative. Select the `behavior_kind` enum and exact role schema below. For ordinary `attack`, `area_attack` chooses the implemented discrete neighborhood pulse instead of direct fire.
   Set `attack_sound` to the existing Bow/Ballista/Rune presentation family. It is captured on admission and never changes targeting or damage. New types reuse those cues; a genuinely new sound family needs an authored asset and bounded playback policy.
   `damage_type` is one of `physical`, `fire`, `magic`, `lightning`, `explosive`, or `ice`, captured by the host. Role/branch mechanics supply a more specific kind for burns, fire operators, bombs/rockets, and Rune evolutions. Enemy `nonphysical_damage_multiplier` composes with bounty vulnerability once; fractional continuous streams apply it to new exposure before flooring HP. This is not a new blanket immunity rule: existing fire/ice status exclusions retain their prior semantics.
5. Reuse an existing special/evolution schema if desired: `second_archer`, direct-fire `pierce`/`bounce` choices, or area `boulders`/`onyx_ring` choices with Boulders' `freeze_runes` follow-up. Copy the corresponding shipped definition for exact fields. Those names are implemented mechanics, not content IDs. Keep the existing schema's prerequisites and mutually exclusive branches.
   Second-archer definitions may supply a flat `advancements` prerequisite graph. Roots omit `requires`; successors name the exact previous key. Records contain title, positive cost, complete active combat properties, optional per-purchase `attack_rate_multiplier`, and `archer_count` (1–8). Supported `weapon`s are `arrow`, `molotov`, `grenade`, `rocket`, `minigun`, and `flamethrower`; copy the shipped schema for paired burn/splash fields and continuous fuel settings. Cyclic/dangling prerequisites and malformed/nonfinite properties reject admission. See [advancement rules](archer-advancements.md).
   Chain/support/economy definitions use the role evolution schemas below. Evolution branches remain inside their parent's collection identity/loadout slot; branch keys are mechanics, never new collectible IDs.
6. Add the **TowerDefinition** reference once to `resources/content_catalog.tres` → `towers`. Do not add another reward list, menu entry, rendering switch, RPC branch, or code constant.
7. Use the [development workflow](development.md#setup) for imports/verification. In an isolated collection, unlock through a chest, select/commit the identity, buy from the palette, inspect, upgrade/reroll, and verify accepted behavior with separate peers. Inspect visual/input changes in the running game; headless success is not pixel or art approval. Commit authored resources and Godot-generated script UID sidecars, not import caches.

Existing saved players keep their unlocks and see the added tower as locked until awarded. Chest exhaustion and reward-count capping automatically include the new entry.

## Six-role schemas and evolution data

The shipped identities are Arrow (`arrow_tower`), Ballista (`orc_ballista`), Rune (`rune_obelisk`), Lightning (`lightning`), War Drums (`war_drums`), and Gold Mine (`gold_mine`). Author behavior through the `TowerDefinition.behavior_kind` enum (`attack`, `chain`, `support`, `economy`), not a switch on those IDs. Evolved `bounty`/`income_aura` kinds occur in branch records, not as base-kind enum options. A novel mechanic still needs its real rule owner; renaming an ID does not add behavior.

| Kind | Exact `behavior_config` keys | `upgrade_effects` | Roll profile / shipped compatible effects |
| --- | --- | --- | --- |
| `attack` | Empty dictionary; `area_attack` distinguishes direct fire from Rune-style pulses | Empty | `attack`: Arrow/Rune `damage`, `attack_speed`, `range`; Ballista also `pierce`, `bounce` |
| `chain` | `hit_count`: positive integer including the first victim; `jump_distance`: positive number; `successive_hit_bonus`: nonnegative number | Empty; ordinary damage/speed upgrades apply | `attack`: `damage`, `attack_speed`, `range`, `chain_jumps` |
| `support` | `stack_group`: nonempty string; `damage_bonus`, `attack_speed_bonus`: nonnegative numbers, at least one positive | Exactly `damage: {damage_bonus: positive number}` and `speed: {attack_speed_bonus: positive number}` | `support`: `range`, `support_buff` |
| `economy` | `clear_income`: positive integer; `periodic_income`: nonnegative integer; `periodic_interval`: nonnegative number. Periodic amount and interval must either both be zero or both positive. | Exactly `damage: {income_bonus: positive number}` and `speed: {income_bonus: positive number}` | `economy`: `economy_production` |
| Evolved `bounty` | Exactly positive `mark_damage_bonus`, `mark_income_bonus` | Retains parent purchases | Parent `economy` profile/effects |
| Evolved `income_aura` | Exactly nonempty `stack_group`, positive `kill_income_bonus` | Retains parent purchases | Parent `economy` profile/effects |

All numbers must be finite. `roll_attributes` is an explicit, duplicate-free compatible subset, including effects safe for future branches. Direct `attack` supports Pierce/Bounce, but the shipped Arrow deliberately does not opt into them; area attacks cannot. Cross-role pools/profiles, extra behavior keys, unsupported branches, and malformed role upgrades fail catalog validation rather than silently falling back.

Every role evolution record has `title` (nonempty string), `cost` (positive integer), `behavior_kind`, and `behavior_config`. Copy the shipped resources for the complete schema:

- **Lightning:** `special_upgrade = "escalating_chain"` requires positive `special_upgrade_config = {successive_hit_bonus: ...}` plus title/cost. Both ordinary stats precede the special, and that special precedes `longer_reach`. The sole currently specified evolution adds `range_cells`, keeps kind `chain`, and must increase both initial targeting range and jump distance. Base chains choose the nearest not-yet-hit enemy at each jump (stable-ID ties), deal full damage per victim, and never hit an individual twice. Escalation multiplies hit index `i` (zero-based) by `1 + i * successive_hit_bonus`. Final identity/name and additional evolution choices were never decided; the implemented Longer Reach and all its values remain provisional, not a claimed complete final tree.
- **War Drums:** mutually exclusive `forge` / `command_banner` records retain kind `support`; Forge has only positive damage, Banner only positive speed. Different `stack_group`s add; duplicates use the strongest applicable value **per component** in each group. Both paid base upgrades survive a pure branch and transfer to its remaining component, then `support_buff` scales that result.
- **Gold Mine:** mutually exclusive `royal_mint` / `bounty_board`. Mint keeps kind `economy`, preserves at least the base clear payout, and adds positive periodic production on combat simulation time, never wall time or interest. Bounty switches to kind `bounty` and replaces production. Its `followups` dictionary contains permanent exclusive `stronger_mark` (both mark bonuses strictly larger) and/or `income_aura` records. The shipped titles are Greater Bounty and Tribute Office, not user-final names. Buying the aura removes that Board's active mark immediately.

### Per-placement rarity authoring

`CombatRules.roll_rules` optionally references `TowerRollRules`; `resources/combat/prototype.tres` enables `resources/combat/tower_rolls.tres`. A newly constructed `CombatRules` leaves it null, intentionally supporting deterministic injected fixtures without placement rolls/rerolls. Null is not a fallback for invalid authored data. The admitted rules are deep-copied and validated against **every** definition's compatible effects/profile before gameplay.

Each of the eight `rarities` dictionaries requires `id`, `title`, finite nonnegative `weight`, integer `positive_slots` / `drawback_slots`, and `positive_pool` / `drawback_pool` dictionaries. Each pool maps an effect name to inclusive `Vector2(min, max)` bounds. Fractional effects are signed bonuses, not final multipliers; `pierce`, `bounce`, `chain_jumps` are positive integer counts. Drawbacks must stay strictly between −1 and 0 and cannot be count effects. Positive bounds must be above zero; all bounds must be finite and ordered. Count bounds must be integral and at most 1,000,000.

`slot_profiles` maps a profile to rarity-specific `Vector2i(positive, drawback)` overrides. Missing rarity overrides use base slots; a missing/invalid selected profile is an error. Validation requires all eight unique tiers, at least two with positive weight, valid cost curves, and enough compatible distinct effects to fill **every requested slot** without a duplicate or an opposing sign of the same effect. Generation chooses only effects that leave the remaining slots fillable; it never truncates an incompatible roll.

The following is the shipped **provisional** configuration, not creator-approved balance. Attack and support use the base slots; economy has only one compatible effect and uses the overrides shown. Weights total 100, but generation normalizes any valid total.

| Rarity | Weight | Attack/support +/− slots | Economy +/− slots | Positive fractional bounds¹ | Positive range | Drawback fractional bounds¹ | Drawback range |
| --- | ---: | --- | --- | --- | --- | --- | --- |
| Broken | 8 | 0/1 | 0/1 | — | — | −35%…−20% | −25%…−10% |
| Shoddy | 13 | 0/2 | 0/1 | — | — | −20%…−10% | −12%…−5% |
| Common | 35 | 1/1 | 1/0 | 3%…8% | 3%…6% | −8%…−3% | −6%…−2% |
| Uncommon | 26 | 1/1 | 1/0 | 8%…15% | 5%…10% | −4%…−1% | −3%…−1% |
| Rare | 12 | 2/0 | 1/0 | 12%…22% | 8%…15% | — | — |
| Epic | 4.5 | 2/0 | 1/0 | 20%…35% | 12%…22% | — | — |
| Legendary | 1.3 | 2/0 | 1/0 | 30%…50% | 20%…35% | — | — |
| Mythic | 0.2 | 2/0 | 1/0 | 45%…75% | 30%…50% | — | — |

¹ `damage`, `attack_speed`, `support_buff`, `economy_production`; eligible pools are intersected with the tower's declared effects. Mechanical positive pools begin at Rare: Pierce/Bounce/chain extra hits respectively are Rare `1/1/1`, Epic `1–2/1/1–2`, Legendary `1–3/1–2/2–3`, Mythic `2–4/2–3/3–5`. They never appear in drawback pools.

Rarity rerolls exclude the current tier and renormalize the **same** base weights, allowing downgrades, then replace all attributes. Attribute rerolls retain rarity and regenerate all effects/values. There is no preview, offered choice, or permanent rolled collection item. Accepted rarity rerolls have a dismissible cosmetic reel, which cannot change the result. Its staged better-rarity neighbor is not an indication of actual odds.

### Effective stats, costs, and payout rules

`MatchCombat` derives effective stats from purchased baselines on board changes, never compounds a prior rolled result. Evolution/reroll preserves paid upgrades; rerolls replace only the rolled part. Damage uses the purchased base times `(1 + rolled damage) * (1 + summed support damage)` and rounds up (with a 10⁻⁹ arithmetic-noise tolerance). Interval divides the purchased base interval by `(1 + rolled speed) * (1 + summed support speed)`; remaining reload scales with the interval. Continuous/Burn effects apply those multipliers and bounty vulnerability inside their fractional accumulators, not by rounding up every simulation step.

Range applies to the active branch's authored base: a positive roll uses `ceil(base * (1 + bonus))`; a negative roll uses `max(min(1, base), floor(base * (1 + bonus)))`; zero preserves the base exactly. This changes usable tiles without enlarging a footprint. Rolled Pierce/Bounce counts work independently and add to their purchased branch capacity; `chain_jumps` adds to the chain's total hit count. Rune evolutions retain compatible damage/speed/range rolls, and Fire/Bomb advancement damage retains its rolled/support multipliers.

Paid support upgrades add to the applicable components before the support roll multiplier. Economy's two paid `income_bonus` values and `economy_production` roll add into one income bonus. Mine/Mint clear and periodic amounts use `ceil(authored amount * (1 + income bonus))`; Bounty's mark payout percentage or the aura percentage instead multiplies by `(1 + income bonus)`. Economy modifiers survive every branch; they do not increase bounty damage vulnerability.

Reroll price is `ceil(base + linear*n + quadratic*n²)`, with independent per-tower accepted-reroll counts `n`. Provisional curves are rarity `(8, 4, 2)` Shards and attributes `(20, 10, 5)` Coins. A rarity reroll resets the attribute count but not its own. Curves require finite base ≥1, linear ≥0, quadratic >0; an invalid/negative count or cost above 9,007,199,254,740,991 disables that action (`-1`), not a free reroll. Sandbox prices are zero. Ordinary paid upgrade pricing remains in [development](development.md#combat-simulation-and-verification).

Bounty selects highest **maximum** HP in range, with stable-ID ties, ignoring already-marked enemies. Its single exclusive mark persists outside range until death/crystal arrival or removal of its source/marking branch; it cannot retarget while active. Stronger marking updates the active mark. Income aura eligibility tests the **killing tower's location**, not the victim's; duplicate auras use the strongest applicable bonus. Final kill payout is `ceil(normal bounty * (1 + scaled mark bonus + strongest killer-location aura bonus))`: combine percentages before one final rounding. `kill_bounty = -1` inherits match bounty. A zero-normal-bounty summon yields zero Coin bonus, but still has its independent Shard drop.

Placement/reroll validation precedes spending or RNG consumption. Rejected actions change no currency, attributes, counters, or gameplay random state. Host-player and remote commands share the validators; committed Ready locks management rerolls until combat. Singleplayer validates both counterparts, samples an accepted result **once**, copies it to both towers, and charges each board independently. Roll and drop RNGs are isolated from regular composition, irregular timing, group/ritual, and result/tie RNGs; cosmetics never draw from gameplay streams.

### Branch artwork

`TowerReward.board_variants` maps real special/evolution/advancement/follow-up keys to required `texture: Texture2D` plus optional `board_height` (positive finite) and `board_anchor` (normalized Vector2). Archer variants may also override finite texture-local `archer_pivot`, `secondary_sprite_offset`, and `additional_archer_offsets: PackedVector2Array`, plus `portrait_bounds: Rect2` relative to the tower foot in cell units with positive finite size. Omitted fields inherit the parent. Active advancements select their own layers; follow-ups take precedence over evolutions. Collection/chest icons stay unchanged. Shared metadata drives board drawing, rig/muzzle placement, grounding, portrait framing, and camera headroom; unknown branches/fields and invalid geometry reject admission.

`tools/author_gameplay_towers.py` reproducibly draws eight original native 96×112 hard-alpha RGBA PNGs into `assets/towers/` using Pillow and integer geometry: Longer Reach, War Drums/Forge/Command Banner, and Royal Mint/Bounty Board/Greater Bounty/Tribute Office. It never overwrites approved base Lightning, Gold Mine or established tower PNGs. Pillow is an offline authoring dependency, not a game dependency. These procedural sprites do not imply final art approval.

Gold Mine now uses the creator-approved, reference-free GameLab 128×128 still, with 48 opaque RGB colors and hard alpha. Its source outputs, exact expanded prompt/settings, processing and hashes, and previous procedural PNG are preserved in `archive_assets/towers/gold-mine/gamelab-20261017/`. The opaque width remains approximately 0.98 cells; its new anchor follows the rock footing, while every unchanged branch explicitly retains its prior anchor. Collection/chest/shop/guide artwork resolve the same identity texture. This is a static art replacement, not a change to income, upgrade rules, footprint, or network state.

Base Lightning also uses a creator-approved reference-free GameLab still. Its 128×128 source has 47 opaque colors; runtime art reframes it losslessly onto a 128×144 canvas with translation `(-16, 11)`, preserving every visible pixel. This aligns the crown with shared projectile coordinates `(48, 19)` without changing the Longer Reach PNG or renderer contract. Opaque width remains approximately 0.98 cells; height is approximately 1.61 cells, with anchor `(0.375, 0.94444444)`. Longer Reach retains its previous anchor and height. Sources and processing are archived under `archive_assets/towers/lightning/gamelab-20261017/`. An isolated Wayland/Mesa main-scene walkthrough exercised pointer placement/inspection, top-row clearance, adjacent Gold Mine, both orientations at standard and compact widths, and live chain fire; base/evolved muzzle geometry and rendered board/icon checks passed. This does not establish native GPU performance or roster-wide art approval.

### Directional weapon artwork

`TowerReward.directional_weapon_textures` and `directional_projectile_origins` are empty for ordinary art or contain eight entries ordered **N, NE, E, SE, S, SW, W, NW**. The full-canvas `icon_texture` supplies fixed framing; `board_texture` supplies stationary masonry. Each weapon texture and bolt-tip coordinate uses that same canvas. Catalog validation rejects partial arrays, missing resources, nonpositive/mismatched canvases and nonfinite/out-of-bounds tips. There is no hard-coded canvas size in rendering.

Ballista's authorized provisional trial uses the aligned 192×192 GameLab set archived under `archive_assets/towers/ballista/gamelab-20261017/`. Drawing selects the layer from the displayed direction to the accepted `target_id`, following that exact live in-range enemy through route interpolation. No renderer-side target search decides gameplay. Missing/dead/out-of-range victims use host-captured `aim`; zero aim selects SE. Mirrored maps reflect the direction only, never the base/light. Accepted shot aim selects and captures a release tip, so later movement or pose changes cannot move an already released bolt. Fixed icon scaling, foot depth and all-layer camera clearance prevent size/anchor changes while aiming.

The trial retains a manually reconstructed roof because the requested empty-base generation was rejected for insufficient credits. The creator explicitly authorized trying the existing set; this does not imply final roof/proportion approval, new animation, changed attack policy, damage, footprint or save format.


`tools/author_arrow_branches.py` derives additive branch layers from the existing archer-free Arrow board texture, preserves source PNGs, and authors dark-haired/muscular operator sheets. `ArrowWeaponVisuals` supplies shared throwing/rocket/rotary/flamethrower equipment and cosmetic animation. Two-storey artwork retains its one-cell gameplay footprint; six extra offsets place the remaining archers. Every Arrow guide node/portrait uses the same battlefield renderer rather than a separate tier image convention. Native48px, both-orientation and actual-main-scene checks are recorded in [archer advancements](archer-advancements.md#verification); those checks do not imply performance or creator art approval.


## Add an enemy using existing movement and damage

1. Create `resources/combat/enemies/<id>.tres` with the `EnemyDefinition` script. Give it a unique, nonempty stable `id`, title, description, texture, source-facing flag, board height, and normalized foot anchor.
   Set presentation-only `elite = true` for an Elite Orcieary entry; otherwise non-boss enemies are Basic. The existing `boss` flag places bosses in the Boss group. The guide derives group order and white/purple/red name colors from those fields, without enemy-ID switches or new gameplay rules.
2. Configure positive health/speed multipliers, base damage, spawn weight, introduction wave, and send cost; income/count-cap/count growth must be nonnegative. `count_cap_growth_interval` is positive; `max_weight_share` is finite in `[0, 1]`. A zero count cap means unlimited. Finite caps grow relative to `first_wave`; share limits cap weight, not head count, and are floored for each wave budget.
3. Add the definition once to `resources/content_catalog.tres` → `enemies`. This registers send choices, regular-wave eligibility, type previews, enemy inspection, sprite/facing/slow presentation, and host-accepted instances. No enemy-name switch or RPC edit is needed.
4. Keep at least one always-unlocked (`first_wave = 1`), non-boss, weight-one, unlimited-count, full-share (`max_weight_share = 1.0`) enemy so every wave can exactly fill its remaining budget. It may have any ID; Grunt is only the shipped choice. An added expensive type can legitimately be absent until the budget and its floored share allowance fit it. Paid sends ignore regular unlock/count/share constraints, as before.
5. Use applicable verification from the [development workflow](development.md#setup). Exercise selection/paid sends during planning/combat, eligible regular rounds, count/share limits, inspection, leaks, and separate host/client agreement. Inspect artwork, facing, damaged-bar readability, and both rendered orientations in the running game; headless checks are not pixel proof.
6. For animated content, assign `animation_frames: SpriteFrames` with a looping `walk`, nonlooping `death`, and optional `heal`/`cast` poses. All frames share canvas dimensions and a fixed `board_anchor`; raised limbs/staff and collapsing bodies must retain transparent canvas margins. Keep `texture` as the matching static first-frame reference. `EnemyVisuals` shares frame selection, slow tint, and alpha picking between board and Orcieary. `blood_color` controls a small ground splatter; use alpha zero for bloodless types and author their debris/bones into the death animation.
7. Configure `send_first_wave` independently of `first_wave`. `regular_spawn_enabled` and `send_enabled` allow summoned-only identities. `group_weights` assigns odds to member counts (index zero is one member); `group_interval` sets within-group spacing. Weight, send cost, and income apply once per group; `kill_bounty` applies per killed individual (`-1` inherits match bounty).
   Set `fire_immune`/`ice_immune` for status immunity. These flags do not prevent direct physical damage and are automatically included in accepted previews/instances and the Orcieary readout.
8. Existing resource-driven abilities are `heal_interval`/`heal_radius`/`heal_fraction`, or `summon_interval`/`summon_cast_duration`/`summon_type`/`summon_min`/`summon_max`/`summon_limit`. Summon references must resolve within the same catalog. Summoners may raise other summoners, but the type graph must be acyclic. Each caster limits its own living direct children, starts its timers at birth, and passes on its captured route/progress. Read the [roster rules](enemy-roster.md) before reusing a behavior.
9. Set `reroll_drop_chance` to a finite probability in `[0,1]` and `reroll_drop_amount` to a nonnegative integer. Either zero disables the effective payout. Each individual death rolls separately for the defending player's run-only **Shards**, including sent/group members and summoned SkeleOrcs; leaks do not grant them. These fields are captured on admission and do not depend on Coin bounty.
10. Set `boss = true` for a single-member encounter reserved before ordinary selection. Its `first_wave` debut is guaranteed when its weight fits the current budget/share; author those values so the intended debut fits. Later eligible waves roll once with `min(boss_spawn_chance_cap, boss_spawn_chance + max(0, round - first_wave - 1) * boss_spawn_chance_growth)`. All odds must be finite, initial/cap in `[0,1]`, initial ≤ cap, and growth nonnegative. A boss never re-enters ordinary selection, so at most one of each type appears per wave; all three types may coexist when their rolls and combined budget fit. Bosses are always unsendable, even if an injected resource enables sends. Shipped debuts are NecOrcmancer Mancer (40), Trollorc (60), and Orc king war orchine (100). Titles may change without changing stable IDs/records.
11. Optional boss abilities use resource fields, not identity switches: stomp interval/radius/HP fraction; `tower_attack_kind` with interval/cast/stun durations and `tower_attack_targets`; and `jump_interval` with four `jump_weights` for lengths 2–5 plus deploy/charge/flight/landing durations. Zero intervals disable actions; disable jumps with empty weights. Club selects the nearest in-range tower; cannon selects distinct random towers across its board. The host captures target ID/aim arrays, route-cell jump endpoints and clocks. No direct terrain/blocker movement schema remains.
12. `summon_pool` plus positive matching `summon_weights` extends a ritual to weighted registered children; an empty pool retains `summon_type`. Every child participates in acyclic summon validation; boss children are forbidden. Children inherit their parent's captured painted route/progress. Incoming `nonphysical_damage_multiplier`, `fire_damage_multiplier`, and `lightning_damage_multiplier` are positive, finite, host-captured values composed once with bounty vulnerability before whole-HP or fractional damage application.
13. Boss art retains a fixed canvas/anchor across poses. `attack`, `jump_deploy`, `jump_charge`, `jump`, and `jump_land` animations consume accepted state. Normal carrier travel uses `walk` wheels. Optional `_damaged` / `_critical` suffixes select at ≤66% / ≤33% maximum HP, sharing framing, shadows, and alpha picking. Stars, projectile traces, doors, and audio consume accepted state/counters; never run a second client-side attack, jump, or stun clock. Stun suspends all tower-role effects; previously applied burns survive independently.
14. `physical_damage_multiplier` extends incoming damage tuning to physical hits/continuous streams. `death_spawn_type` and positive `death_spawn_count` create exact individual children only on confirmed death; their graph is validated together with summon references. `enrage_health_fraction` plus `enrage_speed_multiplier > 1` enables a permanent surviving-hit threshold transition, with `walk_enraged` artwork. `regeneration_interval` and `regeneration_fraction` enable timed self-only healing with `heal` artwork. Disabled pairs retain their zero/one defaults; all values must be finite and valid. `EnemyMechanics` owns these rules, called by the authoritative combat owner.

### Boss reward authoring

`CombatRules.boss_reward_rules` references `BossRewardRules`, enabled in the shipped prototype. Null intentionally disables it for unrelated rule fixtures. The resource references existing `TowerRollRules` rarity IDs/titles/weights and requires strictly ascending positive `Vector2i(Coins, Shards)` payouts for all eight tiers. `BossRewardLedger` captures scalar data at admission and owns per-slot/per-type claims, independent RNG, scaled awards, and detached history. Only confirmed tower kills call `claim`; no UI command awards loot. See [loot rules and payouts](enemy-roster.md#first-boss-kill-loot).


The prototype starts each player with 8 Shards and grants 3 on a surviving round clear (`starting_reroll_currency`, `clear_reroll_currency`). Its provisional per-death chance/amount pairs are Grunt `0.08/1`, Runner `0.10/1`, Brute `0.16/2`, Orcling `0.025/1`, Orc Chief `0.20/2`, NecOrcmancer `0.25/3`, NecOrcmancer Mancer `0.25/3`, SkeleOrc `0.04/1`. Summon farming is intentionally eligible, not silently excluded. Shards, placed rolls, and reroll counters are run-only; they do not enter collection progression.


## Validation and injected catalogs

`ContentCatalog.validation_errors()` returns actionable messages without logging or mutating the resources. It rejects null definitions, missing tower rewards, empty/duplicate IDs within each content kind, missing titles, invalid/nonfinite combat/economy/wave values, unsupported special/evolution schemas, and invalid/nonfinite presentation geometry. A null texture is permitted for non-rendered rule fixtures; authored playable content must supply textures. The normal renderer does not invent artwork for unknown IDs.

`CollectionStore` validates the catalog before loading or granting rewards and exposes errors without replacing an existing save. `MatchCombat` rejects an invalid catalog and requires the exact-fill remainder-enemy invariant before starting combat. Invalid configuration must be fixed, not silently replaced with shipped defaults. A custom collection-only test catalog can have no enemies; an actual combat catalog cannot.

For tests or a custom match, assign `rules.catalog` before instantiating the game/model. Pass that same resource to `CollectionStore.new(save_path, rules.catalog, random)` when injecting a store. `store.catalog` is its derived reward array, while `store.content_catalog` is the owning resource. `CombatRules.new()` owns detached registration arrays, but definitions are shared: duplicate a definition (and its reward when editing identity/art) before tuning it. There are no legacy parallel-list overrides.

`tests/content_catalog_test.gd` exercises a catalog containing no shipped IDs through saved chest unlocks, actual main-scene UI, mirrored authoritative purchases and sends, exact-fill waves, accepted snapshots, renderer artwork lookup, and both second-archer muzzle origins. Existing combat, collection, palette, and rendered board regressions retain their behavioral coverage.

## Existing behavior versus novel mechanics

Resources can change stats, identity, existing artwork/geometry, wave/send tuning, and select the already implemented attacks/evolutions above. They do not implement arbitrary behavior. A new damage/status model, targeting policy, projectile impact rule, movement/routing rule, upgrade branch, footprint, or evolution needs code in its existing rule owner, matching presentation, host snapshot/command handling where relevant, and behavioral regressions. Do not advertise a novel mechanic only in a resource description or add an ID-specific exception to imitate it.
